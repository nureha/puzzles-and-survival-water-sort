# 最大露出 partial 手順（? をできるだけ多く判明させる）設計

## 背景と目的

`?` を含む盤面で推定解が得られなかったとき、現在の `solvePartial` は BFS で「最初に `?` を1個露出できる状態」に到達した時点で打ち切り、露出手を1手だけ後付けして返す。ユーザーは 1個判明 → 入力 → 再探索 を繰り返すことになり、ゲーム画面との往復が多い。

本設計では、この partial 手順を「**1回の手順で露出できる `?` の数を最大化する**」ものへ置き換える。起動は自動（partial に落ちたときは常に新方式）で、UI トグルは追加しない。

判明後の盤面が解きにくくなる可能性は許容する（露出数を最優先する方針を採用）。最大露出手順の接頭辞には最初の露出が含まれるため、既存のステップ UI で途中まで実行して打ち切り、早期に再探索することも従来どおり可能である。

## 前提となる不変条件

`isValidMove`（`src/solver/bfs.ts`）は、トップが `?` の試験管からの注ぎと、トップが `?` の試験管への注ぎを両方禁止している。したがって:

- 探索グラフはもともと「既知セルだけを動かす手」に限定されており、`?` の実際の色に依存しない。手順は必ず実盤面で再現できる。
- **トップが `?` になった試験管は以降 from にも to にもなれず、永久に凍結する。**

## アルゴリズム: `solveMaxReveal`

`solvePartial` を置き換える。

### 露出数

```
revealed(S) = |{ i : top(S[i]) === '?' }| − |{ i : top(S0[i]) === '?' }|
```

凍結の不変条件により `{ i : top(S[i]) === '?' }` は経路に沿って単調増加するため、初期値の引き算で正しく数えられる。

### 理論上限

```
MAX = |{ i : S0[i] が '?' を含む ∧ top(S0[i]) !== '?' }|
```

到達可能とは限らない上限。`best === MAX` に達した時点で探索を打ち切る。

### 探索

既存と同じ手グラフを BFS で層順（＝手数順）に探索する。

- 状態 `S` を展開するたび `revealed(S)` を評価し、現在の `best` を超えたらその状態と経路を記録して `best` を更新する。
- BFS が層順であるため、**同じ露出数なら最初に記録されたものが最短手数**になる。追加のコストは不要。
- `best === MAX` で即終了。
- 探索予算超過時はその時点の `best` を返す（部分的な最大化）。

### 末尾に無駄手が残らないことの保証

`best` を `k` に更新した状態 `S` への最短経路の直前状態を `S'` とする。もし `revealed(S') === k` なら、`S'` の方が短く露出数 `k` なので BFS 順で先に `best = k` が記録されていたはずで矛盾する。よって `revealed(S') < k` であり、**記録される経路の最後の手は必ず露出手**。末尾の刈り込み処理は不要。

### 実装上の注意: メモリ

現在の `solvePartial` は最初のヒットで打ち切るため、キューのノードに `moves` 配列をコピー保持している（`[...moves, move]`）。全探索ではこれが O(状態数 × 深さ) となり破綻する。

**親ポインタ方式に変更する。** ノードを `{ state, parent, move }` の配列で持ち、インデックスで親を辿る。最良状態が確定した時点で経路を逆順に復元する。

探索予算は `MAX_STATES`（= 1,000,000、具体色ソルバー用）とは別の定数 `REVEAL_MAX_STATES` を用意し、**初期値 200,000** とする。`?` を含む盤面は自由度が低く到達状態数が小さいため、実装時に最大構成（試験管20本）で実測し、探索が予算に張り付くようなら調整する。

### 削除されるコード

露出は「トップが `?`」で直接判定できるため、人工的な露出手の後付けが不要になる。以下は削除する:

- `findRevealHints`
- `partialWithReveal`
- `firstValidDest`

## 型の変更（`src/solver/types.ts`）

```ts
export type Move = {
  from: number;
  to: number;
  isSpeculative?: boolean;
  revealsTube?: number;   // この手で ? が露出する試験管
};

export type RevealHint = {
  tubeIndex: number;
  stepIndex: number;      // 何手目（0 起点）で判明するか
};
```

- `RevealHint.description` は削除する。文言は `SolutionList` 側で生成する。
- `SolveResult` の `partial` バリアントの形（`{ type: 'partial'; moves: Move[]; revealHints: RevealHint[] }`）は変更しない。

1手は from 1本・to 1本しか動かさず、to のトップは注いだ既知色になるため、**1手で露出する試験管は高々1本**である。よって `revealsTube` は単数で足りる。

`revealsTube` と `revealHints` は、確定した経路を初期状態から再生し、各 `applyMove` の直後にトップが `?` になった試験管を検出して付与する。

## UI（`src/components/SolutionList.tsx`）

### 各ステップの印

`MoveList` の行に、`move.revealsTube` が定義されていれば注記を追加する。

```
3. 試験管1 → 試験管3
4. 試験管5 → 試験管2   ← 試験管5 の ? が判明
```

### 見出し

現行の「? を判明させる手順（最後の手で ? が上に出ます）:」は1個露出前提のため、露出数を反映した文言へ変更する。

> ? を判明させる手順（3個の ? が判明します）:

### 末尾サマリ

`revealHints` から生成する。

> すべて実行すると **試験管2・5・7** の ? が判明します（3個）。判明した色を入力して「この盤面から再探索」を押してください。

### 露出0のケース

現行は `moves` も `revealHints` も空になり、上部の警告文だけが残って手順欄が無言で消える。ユーザーが次に何をすべきか分からないため、明示メッセージを表示する。

> 動かせる既知のブロックが無く、? を判明させる手順がありません。

## `src/App.tsx` への影響

**変更なし。**

手順を最後まで実行すると複数の試験管でトップが `?` になり、ユーザーがそれぞれに色を入力する。`handleTubesChange` の reveal 分岐（`App.tsx:114`）は `detectReveal` が「1セルでも `?` → 具体色」で true を返すため、複数同時判明にそのまま対応する。解と進捗を保持したまま盤面へ反映され、既存の「この盤面から再探索」で解き直せる。

`applyRevealToEntry` による active entry への自動保存も、partial の露出手順は `?` セルを動かさないため既存の想定どおり安全に動作する。

## テスト

### `src/__tests__/bfs.test.ts`（追加）

- 2本以上の `?` を1手順で開ける盤面 → `revealHints.length` が期待値と一致する
- 露出数が同じ経路が複数ある盤面 → 手数が短い方が返る
- 上限 `MAX` に到達する盤面 → 末尾が露出手で、余計な手が付かない
- 各 `Move.revealsTube` が、その手を適用した直後にトップが `?` になる試験管と一致する
- 露出不能盤面 → `moves` 空・`revealHints` 空

既存テスト（`reveal hint points to tube where moving top exposes ?` ほか）は `tubeIndex` と「最後の手が露出手」のみを検証しており、いずれも新設計で成立するため改修不要。

### `src/__tests__/SolutionList.test.tsx`（追加）

- `revealsTube` 付き手順でステップ印が表示される
- 複数 `revealHints` で末尾サマリに全試験管番号が並ぶ
- `moves` 空・`revealHints` 空で「手順がありません」メッセージが表示される
